# 任务进展与跟进

在项目的「项目设置」中启用「自动检查任务进展」。选择时区、工作开始和结束时间，以及每天的检查时间。时间表按项目存入 SQLite，默认关闭。周一至周五运行，每个项目可设一到六个检查时间。检查只在推进中的项目运行，自动派工可以独立关闭。

例如上海时间工作日 10:00 和 16:00 检查，工作时段为 09:00–18:00。对应的项目配置如下。通过项目变更 API 修改已有项目时仍需传入当前修订号。

```json
{
  "name": "2048",
  "autoAdvance": false,
  "tracking": {
    "timeZone": "Asia/Shanghai",
    "times": ["10:00", "16:00"],
    "workHours": { "start": "09:00", "end": "18:00" }
  }
}
```

关闭自动检查时将 `tracking` 设为 `null`。暂停或归档也会停止该项目的自动检查。从休眠或离线恢复时，工作时段内最多补查最新一次错过的时点，之后照常按原时间表执行。时区按当地日历解释，工作结束时刻不含在工作时段内。

## 两种触发，共用一个判断

| 触发 | 操作与范围 |
| --- | --- |
| `tracking.ping.requested` | 在任务详情选「跟进进展」，或在项目群引用任务说「麻烦跟一下这项，看看试玩前还缺什么」。项目 Agent 理解指代并调用 `tracking.request`。只检查指定任务，可看其上游事实。查状态可直接回答 |
| `tracking.check.due` | 定时器向有序队列登记项目 ID 和计划时点。一次分析看当前未完成任务，包括待依赖、待验收和排队任务 |

[默认事件配置](../../config/events/tracking.defaults.json)在 `sources.tracking` 下，包含两个事件的说明和开关。可在「项目事件配置」独立停用、编辑描述或补充 Agent 指导。自动事件开关与项目时间表同时生效。

两种触发都根据当前任务、截止日期、负责人、相关交付、工单报告和已记录进展判断是否提问。每轮最多向一人发一条跟进。当前工单在等某位成员补证据时，Agent 需引用该工单并选中原文明确点名、项目中可唯一核实的成员。只有真实提交了交付，才进入待验收。无法确认工单的当前待处理人时保持安静。

同一任务的人工和自动检查共用 24 小时冷却。待投递的提醒在发送和重试前重新核对进展、依赖、收件人和群绑定。群内手动触发保留来源平台，网页和时钟根据可用绑定选择通道。推进记录显示 Agent 建议、跳过原因、Outbox 状态和已知重试错误。平台超时后可能无法确认对方收到几条，以记录中的实际回执为准。

人工跟进可以在工作时段外主动发起。群聊继续按现有机器人接收范围工作。启用飞书时，主动跟进通过机器人发送到已允许的项目群，并用与当前应用匹配的成员 Open ID 提及负责人。 [飞书 CLI 的群发接口](https://github.com/larksuite/cli/blob/main/skills/lark-im/references/lark-im-messages-send.md)

## 写回进展

任意任务都可以从详情选「记录进展」，写明实际结果、可选卡点和证据链接。项目成员也可以在群里引用任务报告成果，由 Agent 通过同一个领域操作登记。详情保留作者、时间、来源与群聊原文，原作者可追加更正。待验收和待答复显示当前对象或版本。

以 2048 为例，试玩任务 C 需要 B 的可运行版本。等待期间，C 可以记录已整理的键盘、触屏用例和已确认的测试设备，卡点写还缺试玩链接。定时检查会读到 C 的准备成果和 B 的当前交付状态，据此判断是否值得跟进。记录这些事实不会推进任务状态或发起验收。

## 2048 群聊验收单

打开看板，进入用于验收的 2048 项目。先跑定时检查，再跑主动跟进。同一任务在 24 小时内的两种触发会去重，所以用两个不同任务验证两次实发，或在第二次检查记录明确的冷却结果。

查询交付时，在群里直接说「帮我看看 2048 的 MVP 做到哪了。最新的测试结果对应哪个版本？离提交验收还差什么？」Agent 根据关联工单和交付记录回答。证据不足时说明哪些信息仍待确认，例如追问「最新的试玩结果发在哪里了？」

| 检查 | 操作 | 通过条件 |
| --- | --- | --- |
| [ ] 群和成员可用 | 确认项目已绑定验收群，并给「人工试玩并整理首版验收结果」指定一名已绑定群聊账号的成员。用该账号 @ 机器人问「人工试玩目前在等什么？」如果提示登记，先按提示把账号登记到项目 | 群里收到当前状态答复，推进记录能看到入站和处理结果。此轮无跟进请求、无任务状态变化 |
| [ ] 几分钟内定时触发 | 在「项目设置 → 自动检查任务进展」开启检查，把时间表暂时设为项目当地时间的两三分钟后。例如当地时间 09:50，填 `09:53`。确认该时间在工作时段内，保存后等待，到点前无需在群里发消息 | 到点后推进记录出现一条 `tracking.check.due`。Agent 有具体问题时，群里收到一条提醒并提及对应负责人。「通知回执」显示已发送。如果没有问题，推进记录能解释本轮为何保持安静。若 Agent 选择了更紧急的上游任务，核对上游收件人和判断理由 |
| [ ] 引用回复写回 | 负责人引用提醒并 @ 机器人，报告真正做完的准备，例如「我已列出触屏滑动和重开用例，实际试玩还在等可运行链接」。如果本轮跟进了上游，打开看板在试玩任务点「记录进展」测试网页写回 | 试玩任务的「进展记录」显示实际结果、作者和来源。等待上游时仍可记录，任务状态和原依赖按实际情况显示 |
| [ ] 手动跟进与去重 | 引用试玩任务并 @ 机器人说「麻烦问一下负责人，试玩前还有什么准备工作可以先做」。也可在任务详情点「跟进进展」 | 推进记录出现 `tracking.ping.requested`。该任务刚被提醒过时，符合 24 小时冷却，或 Agent 根据新进展判断本轮无需跟进。另选一项有明确待确认事项、负责人已绑定且未被跟进的任务，可核对一次新的实际回执 |
| [ ] 恢复项目设置 | 验收结束后，把临时检查时点换成团队使用的时间表，或关闭「自动检查任务进展」 | 再次打开项目设置，能看到保存后的时间表或关闭状态 |

先看「推进记录」定位问题。没有 `tracking.check.due` 时核对项目状态、时区、工作日和保存的时间表。已产生事件时，查看「记录进展跟进的决定和实际登记结果」，再核对「通知回执」里的已发送、待发送、丢弃或重试错误。机器人显示已连接只证明 Stream 已握手，群里收发需要第一项验收确认。
